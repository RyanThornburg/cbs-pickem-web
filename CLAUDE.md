# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Vite + React + TypeScript dashboard for the "Morlocked" NFL pick'em league, live at <https://morlocked.rattsnest.com/>. It's a read-only viewer: a separate data-gathering project polls CBS/Sports IO/ESPN/The Odds API/Pirate Weather into Cloudflare D1 and precomputes per-week/season JSON into Cloudflare KV; this repo's Cloudflare Worker (`worker/index.ts`) serves that KV data over a small REST API, and the React app polls it. There is no write path anywhere in this repo.

## Commands

- `npm start` — Vite dev server (localhost:3000). `/api/*` is proxied to `http://localhost:8787` (`server.proxy` in `vite.config.ts`), so pair this with `npm run dev` in another terminal to get live API data.
- `npm run dev` — `wrangler dev --remote`: runs the Worker + static assets locally against the real production KV namespace (there's no separate local/preview namespace — the Worker never writes, so this can't corrupt prod).
- `npm run build` — typecheck (`tsc -p .`), then the production build to `build/` (the directory `wrangler.jsonc` serves). `npm run preview` serves that build locally.
- `npm run deploy` — `wrangler deploy`, ships the Worker + `build/` to Cloudflare. Its `predeploy` hook runs `npm run test:all` first, and a failing test stops the deploy (calling `npx wrangler deploy` directly skips the tests). Pushes to `main` also deploy automatically (user, 2026-10-02), so a push is a deploy; a manual deploy still needs `npm run build` first.
- `npm run tail` — `wrangler tail`, stream production Worker logs.
- `npm run types` — `wrangler types`, regenerate the `Env` type from `wrangler.jsonc`.
- `npm test` — Vitest in watch mode, app and Worker together. Two projects in `vite.config.ts`: `app` (`src/**/*.test.ts(x)`, jsdom, global `describe`/`it`/`expect`/`vi`, jest-dom matchers) and `worker` (`worker/*.test.ts`, node). The app project passes `--no-experimental-webstorage` because Node 25's own `localStorage` global shadows jsdom's.
- `npm run test:all` — everything once (what `predeploy` runs). `npm run test:worker` runs just the Worker project.
- `npx vitest run -t "test name"` — a single test by name; `npx vitest run defaultTab` — a single file.
- `worker/testHelpers.ts` signs real RS256 Access tokens and stubs the team's certs URL, so `access.ts` is tested end to end. Worker imports name the `.ts` file (`./access.ts`, `allowImportingTsExtensions` in `worker/tsconfig.json`).
- `npm run lint` — ESLint 9 flat config (`eslint.config.js`: typescript-eslint recommended plus the react-hooks rules) over `src/` and `worker/`. Not part of the build; run it before committing.
- `npm run format` — Prettier over `src/` and `worker/` (`.prettierrc.json`: double quotes, ES5 trailing commas). `npm run format:check` reports without writing. The one-time reformat commit is in `.git-blame-ignore-revs`.

Vite gotchas: no `require()` in app code (team logos come from `import.meta.glob` in `utils/teamAssets.ts`), and a CommonJS-only dependency's default export can arrive double-wrapped in the production build but not in dev or tests (why `react-ga4` is on v3, which is ESM). Check `npm run build && npm run preview` in a browser after adding a dependency.

## Architecture

### Data flow: Cloudflare Worker + KV, polled from the client

- `worker/index.ts` is a thin, read-only passthrough: it maps request paths to KV keys (`meta:current`, `meta:historical`, `week:{season}:{weekNN}:{games|leaderboard|odds|trends|recap}`, `season:{season}:{trends|standings}`, `team:{season}:{team_id}`, `user:{id}:season:{season}`, `game:{season}:{game_id}:details`) and returns the KV value as JSON, or 404. Anything outside `/api/*` falls through to `env.ASSETS` (the built static site). Public reads need no auth; the one exception is `/api/admin/*` (see Admin below). There's no `.put()` anywhere — nothing here can write to KV.
- `src/api/pickemApi.ts` has the client-side primitives: `fetchJson` (one-shot), `poll`/`pollJson` (run immediately, then on an interval, until the returned cleanup is called). Cloudflare has no Firebase-style push, so every data hook here polls instead of subscribing — poll intervals vary by how time-sensitive the data is (60s for games and the leaderboard, 5min for odds/week trends/`meta`, 30min for season trends and per-user season data).
- Data access lives in `src/dashboard/data/`, one file per resource, all following poll → parse → callback (returning the stop function): `GetGameDataByWeek.ts` (games; a thin wrapper around `weekGames.ts`, used by Scoreboard and the live-dot tab badge), `GetGamesTabData.ts` (joins games + odds for the Games tab), `GetUserByWeek.ts` (leaderboard + picks), `GetTrendsByWeek.ts` / `GetSeasonTrends.ts` (Trends tab), `GetUserSeasonTrends.ts` (per-user season data for the User Picks badges), `GetStandings.ts` (NFL standings, one team's key, all 32 team keys for the standings' Pool column, and one player's season key; the NFL and player pages wrap these in cached hooks, `Nfl/useNflData.ts` and `Players/usePlayerData.ts`), `GetAdminStatus.ts` (Admin tab), `GetHistorical.ts` (Records tab, `meta:historical`), `GetRecapByWeek.ts` (the week's recap; only reads keys whose `version` matches `RECAP_VERSION`, since the data repo bumps it on any rename or shape change, and treats anything else as no data). `GetGameDetails.ts` is the exception: a one-shot fetch of a game's details key, made only when its Scoreboard box score panel is opened.
- `weekGames.ts` is the shared core all the games-related fetchers build on: one `ApiGame` interface for the full `/api/weeks/:season/:week/games` payload (every caller hits the same endpoint), `toGame`/`toTeam` mappers, and shared helpers (`buildGamesById`, `findEarliestGame`, `getGameCoverResult`). Extend this rather than adding a second parallel game-parsing interface for a new consumer.
- `GetUserByWeek.ts` re-ranks client-side: the API's own `place`/`second_half_place` rank on `cumulative_score` alone, but the UI displays `cumulative_score + trending_score`, so ranks are recomputed against the displayed score (standard competition ranking — ties share a rank, the next rank skips accordingly). It also pads TBD pick placeholders, gated on `has_submitted_picks` — which can be *absent entirely* early in a week, not just `false`, so it's treated as unknown rather than "not submitted" whenever real picks already joined.
- Weeks are zero-padded to two digits in KV keys / Worker routes (`week:2026:03:games`), but passed around the app as plain numbers (`/api/weeks/2026/3/games`).

### State: one context, one orchestrator, everything else prop-drilled

- `CurrentWeekContext` (`src/dashboard/components/CurrentWeekContext.tsx`) is the only app-wide state: it polls `/api/meta` and holds `season`, `currentWeek`, `secondHalfStartWeek`, derived `isSecondHalf`, `cbsPoolUrl` and `paidPlaces`. It also exposes `metaStatus` (`loading` until the first meta arrives, `failed` while that first load keeps failing, then `ready` for good; later failed polls keep the last meta) and `retryMeta`. Until meta is ready, `MainGrid` renders the header and tabs around placeholders with `AppShellStatus` as the body (skeleton rows, or a retrying error with "Try now"), and the first load retries every 15s instead of the 5min poll. The second-half boundary is a data field (`second_half_start_week` from `meta:current`, set by hand each season on the data side), not a hardcoded week number.
- `MainGrid.tsx` is the real orchestrator: it reads `currentWeek`/`season`/`secondHalfStartWeek` from context but derives its own `selectedWeek` (the week the user is browsing, independent of `currentWeek`) from the URL: `?week=3`, absent for the current week, carried across tab changes, with a "Past week · Back to week N" marker in every weekly tab's `TabIntro` while it's set (`PastWeekContext`). Its polling lives in hooks in `useWeekData.ts`: `useWeekData` (the browsed week's `userList` via `GetUserByWeek`, cleared on a week change, plus `leaderboardStatus` (`updatedAt`/`failed`) for User Picks' skeleton, error and "Updated" states; the recap; the live-game flag; and `weekComplete`, every game final), `useSelectedUser` (selected user id, persisted to `localStorage` under `"user"`) and `useIsAdmin`. MainGrid also builds the header: on desktop a small site name, the pick tiles, the Week pill and the player card (`UserSelectDropdown` with `summary="card"`, which shows place, score and money lines inside the select); on phones the Week pill and a compact picker on one row. The selected player's money standings come from `UsersTable/useMoneyStandings.ts` (only prizes in the money or within reach, see `shownMoneyStandings`) and feed both the desktop card and, on phones, the paid-line notes and `PinnedPlayerRow`. It threads these down as props to each tab's component (`UsersTable`, `GamesCard`, `Scoreboard`, `TrendsSection`) rather than via context — check `MainGrid.tsx` first when tracing how a prop reaches a leaf component.
- Tabs are real routes, not local state: `/picks`, `/nfl`, `/trends` (`App.tsx` + `useParams`/`useNavigate` in `MainGrid.tsx`). The last-visited tab persists to `localStorage` (`utils/defaultTab.ts`); a true cold start (nothing stored yet) defaults to `/picks`. An unrecognized `:tab` value redirects through `/` to re-resolve. **NFL** (since 2026-10-02) holds three views in `?view=`: `games` (the Games tab's content), `live` (the Scoreboard) and `standings`; the old `/games` and `/scoreboard` routes (and a stored last tab of either) redirect to the matching view, keeping `?week=`. Plain `/nfl` picks a view (`Nfl/nflView.ts`, tested): one chosen by hand earlier in the visit (sessionStorage `"nflView"`), else the user's rule, Live while any game is live or from the Sunday 1 PM ET deadline through the end of Monday, Games otherwise (it waits for the games poll's `liveKnown` before choosing Games); Standings never opens on its own. The switch (`NflViewSwitch`) sits on each view's `TabIntro`, and the live dot moved to the NFL tab and the Live segment. Team pages are `/nfl/teams/:slug` (the normalized abbreviation, `jac`/`lar`/`was`; resolved to an id through the standings) and stay under the NFL tab. Player pages are `/players/:id`; plain `/players` is the **You** tab (the selected player's page, or a "Who are you?" list that sets the selection when no one is picked). You is only lit on the selected player's own page. Team marks link to team pages everywhere (`shared/TeamLink.tsx`, styled as the plain mark until hover/focus) except the User Picks pick tiles; player names link through `shared/PlayerLink.tsx`. User Picks rows open the player page (the row expand and its trend panel moved onto that page). `/records` (all-time Records, public), `/players` and `/admin` (admin-only) are deliberately not `PrimaryTab`s, so they're never persisted or used as a landing tab. Both sit after a divider in the desktop tab row. From `md` up the tab row sticks to the top once the header scrolls away (and then names the week and player); below `md` the tabs are `PhoneTabBar`, fixed to the bottom of the screen (Picks, NFL, Trends, Records, You, plus Admin for the admin), and the CBS link moves into the header row. Every tab change scrolls to the top (`goToTab`). Both tab rows are links to the routes (`tabLinks.ts`: a plain click stays in the app through `goToTab`; middle/cmd-click opens a new tab), marked with `aria-current="page"`; desktop keeps MUI `Tabs` for the look but overrides its tab roles and roving focus. The weekly tabs (and NFL's Games and Live views) stay mounted while hidden, but their polls (Games, Scoreboard, Trends) pause through `TabActiveContext`/`useTabActive` and refresh as soon as the tab is shown; Standings, team and player pages mount only while open; MainGrid's own week polls (leaderboard, recap, games for the live dot) always run. Records and Admin are `React.lazy` chunks. A "Skip to content" link comes first, each tab has a visually hidden `h2`, and a `?week=` that isn't a past week is dropped from the URL (`03` becomes `3`). Anything else that sticks to the bottom on phones sits on `PHONE_TAB_BAR_OFFSET`, which includes a CSS variable: while a past week is browsed and the shown tab's past-week marker has scrolled off screen (an IntersectionObserver in MainGrid), `PhoneTabBar` grows a 40px "Week N · past week" strip, and the offset grows with it. The header (Week pill, player card with its money lines, and the "Picks" tiles, labelled neutrally since the selected player isn't always the viewer) is identical on every tab except Admin, Records included (the Week pill there sets the week the header's picks and place are from), so it never changes shape on a tab switch; the desktop card keeps a 360px minimum width for players with no money lines. Every tab opens with `TabIntro` (a visible h2 "Games · Week 4", the past-week marker, an optional note like the odds time, the tab's own controls on the right; section titles inside a tab are h3, cards h4): Games, Scoreboard, Trends and Admin render their own, and MainGrid renders it for User Picks, Records and the loading shell. Loading placeholders are `TabSkeleton` (`rows`/`cards`/`tiles`), still and faded once a load has failed. The last `cbs_pool_url` is kept in localStorage (`"cbsPoolUrl"`) so the CBS link survives a meta outage.

### Types

- `src/dashboard/types.ts` is the single source of truth for the API data shapes (`RankedUser`, `Game`, `Team`, `Book`, `MarketSpread`, `WeekTrends`, `SeasonTrends`, etc.) and status enums (`GameStatus`, `Possession`). These map to the Worker's KV-backed JSON responses — there's no schema/codegen, so if the data repo changes a KV shape, update this file by hand (check `CLAUDE.local.md` for the latest confirmed shape changes before assuming a field's shape).
- Odds quirk worth knowing: in `BookMarketSide`, `market=total` has no dedicated Over/Under field — `home_point`/`home_price` is the Over line/price, `away_point`/`away_price` is the Under (the data repo reuses the spread/moneyline columns for totals). See the doc comment on `BookMarketSide` in `types.ts`.

### Component structure

- `src/dashboard/components/` holds one directory per dashboard tab/widget: `GamesCard` (odds + weather, desktop/mobile split; `gamesCardUtils.ts` holds the "is this notable" thresholds — `WEATHER_THRESHOLDS`/`BIG_MOVE_PTS`/`CBS_DIVERGE_PTS` — as frontend config, deliberately kept out of the data pipeline since these get retuned during the season), `Scoreboard` (live scores: full-card `GameCard` and compact `GameRow` layouts, built from pieces in `components/shared/`. Games are always ordered live → upcoming → final, each by kickoff, and never re-sorted, not even for the selected user. Their games are instead summed up in the "Your picks" strip above the list (`YourPicksStrip.tsx`: one chip per revealed pick with the clock, the line and the margin in words, "Covering by ½" / "Needs 4 to cover"; tapping a chip scrolls to and focuses that game's card or row, via `gameAnchorId`). It replaced the "My picks first" switch in October 2026. The layout choice persists to `localStorage` (`"scoreboardLayout"`). The Scoreboard shows no standings or places; those stay on User Picks. The pure logic is in `utils/` and unit-tested: `scoreboardUtils.ts` has cover math, grouping/order, your-pick state and its wording (`pickStateText`, `pickTally`), the ball spot and drive start (both in the feed's home-goal-line frame; the field strip draws away on the left), and the `CLOSE_GAME` highlight-border thresholds, which are frontend config like `WEATHER_THRESHOLDS`. `teamStats.ts` has the box score's split-bar rows (giveaways, penalties and punts are lower-is-better) and the fixed away-blue/home-orange `STAT_BAR_COLORS`. `teamData.ts` has team logo/color lookups. The "Box score and leaders" panel (`GameDetails`) opens on live and final games: leaders and scoring plays come from the games feed, and team stats from `/api/games/:season/:id/details`, refetched every 60s while a live game's panel is open), `TrendsSection` (Trends tab; Week/Season is a segmented control (`ToggleButtonGroup`, like Scoreboard's layout toggle), `?view=` in the URL, remembered in localStorage `"trendsView"`; without a `?view=`, it opens on Season whenever the week has nothing yet (no pick split and no week recap items, i.e. before kickoff). Week: a "Recap" row of this week's items led by the selected player's "You this week" card, then "How the pool split" (Consensus) and "Only one on a team". Season: the season-scope recap cards, the two charts, a 4-column team table (top 10, "Show all 32") and the all-alone log (latest 5). Line Movers was removed; Games already shows moves. Trend data starts `undefined` so loading shows skeletons, a failed poll shows an error, and switching weeks clears the old week), `UsersTable` (leaderboard/picks grid; desktop `UserDataGrid` + mobile `UserDataMobile`, both plain MUI `Table` driven by `@tanstack/react-table` **v8** with shared column defs in `usersTableColumns.tsx`; not MUI X DataGrid, which was removed), `Recap` (the week's recap, called "tidbits" before the data repo's v3 rename; the rotating strip on User Picks: top 8 as ranked by the data, unseen ones first via per-week ids in localStorage `"recapSeen"`, full `headline` on desktop and the 80-character `short` on phones; `recapCategory.tsx` has the category icons (one neutral tile for all; categories aren't results, so no per-category colors). `recapBadges.ts` has the id-based lookups for recap items shown in context, all unit-tested: mover arrows and a gold 5-0 next to names on User Picks (no 0-5 badge on rows, deliberately), "Upset of the week" / "Won, didn't cover" tags on Scoreboard games, and cover/miss streaks of 3+ as a line under the matchup on Games. Recap items are split by `scope` (`itemsForScope` in `weekCards.ts`): week items on Trends › Week, season items on Trends › Season, so cards carry no scope tag. Each view shows at most 4 cards (one row on desktop; 3 when the You card takes a slot) picked by the rule in `weekCards.ts` (unit-tested: chaos index and pool accuracy always, then groups not shown anywhere else; the pool splits card, then badge groups, only fill a short row). The "All N notes" toggle sits on the heading row and opens that view's full list above the cards. Gold chips are for 5-0 only; an upset's believers are plain. Trends › Season also has two hand-drawn SVG charts from the key's `series` (`SeasonRecapCharts.tsx`: pool accuracy by week with 5-0/0-5 names in tooltips, and chaos index bars). The charts draw at their measured width so text stays 11px on phones, and thin the week labels when columns get narrow), `UserAvatar`, `RecordsSection` (Records tab, in this order (the user's "trophy room" pick, 2026-10-02): the selected player's all-time line (`YourRecord`), every champion at once (`ChampionsWall`: a tile grid from `sm`, a list on phones), "Every season" tables opening on Finishes by year (then All-time and By season; `?view=`/`&year=` in the URL, last table remembered in localStorage `"recordsView"`), and six record tiles last. All-time rank is top-10 points (`FINISH_POINTS`: 10 for a title down to 1 for 10th, summed; ties → titles → avg finish; `byAllTimeRank`/`allTimePlaces`), chosen so one great season can't outrank a long good career. The Finishes grid always lists players in that order and uses the leader cards' gold/silver/bronze for 1st–3rd, then slate. The pure math is in `recordsUtils.ts` and unit-tested. `meta:historical` quirks it handles: standings only include players still on file so ranks skip, the 2015/2016 champions are an `"??? unknown/missing user"` placeholder, and half-season results exist only from 2025, and then only for the paid spots).
- `Leaders/` has the Overall and 2nd-half leader cards at the top of User Picks, shown only from `second_half_start_week`. Rows are the paid places (`paid_places` from `meta:current`, in `CurrentWeekContext`), and everyone tied at the cutoff is included. Each row shows the score, picks covering now as a green "+N", and the gap to 1st. The selected user gets their own row below a "···" if they're outside the list. Two cards on desktop, one card with tabs on phones. The row logic is `leadersUtils.ts` (unit-tested), built on `GetUserByWeek`'s ranks, so there's no extra fetch.
- `src/dashboard/icons/` has one PNG per NFL team, referenced by team abbreviation; `utils/teamAssets.ts` normalizes KV team abbreviations that don't match `Scoreboard/utils/team_data.json`'s ESPN-derived keys (`TEAM_ABBR_ALIASES`) before logo/color lookups.
- MUI is v9 on React 19. v9 removed system props, so layout and typography values go in `sx` (`<Stack sx={{ alignItems: "center" }}>`, not `<Stack alignItems="center">`); TypeScript rejects the old form. `Grid` is the v2 grid (`size={{ xs: 12, md: 6 }}`), imported from `@mui/material/Grid`.
- `src/dashboard/shared-theme/` provides the MUI theme setup (`AppTheme` plus `customizations/`). The app is effectively **light-only**: `themePrimitives.ts` defines `colorSchemes`, but `AppTheme` doesn't pass them to `createTheme`, and there's no mode switcher (the MUI Dashboard template's were removed). The theme runs on CSS variables, so if dark mode is ever enabled, detect it with `useColorScheme()` or `theme.applyStyles("dark", ...)`. `theme.palette.mode` won't track it, and a few older spots (User Picks row colors, the avatar tile) still check it that way.

### Worker

- `worker/index.ts` + `wrangler.jsonc` are the entire backend: one `fetch` handler, a single KV binding (`PICKEM_KV`, no named environments — `wrangler dev --remote` and `wrangler deploy` both read the same prod namespace), and static-asset serving (`assets.directory: ./build`, SPA fallback via `not_found_handling`). `workers_dev`/`preview_urls` are off so the custom domain (where Access sits) is the only way in.

### Admin (Cloudflare Access)

- `/admin` and `/api/admin/*` are guarded by a **Cloudflare Access** app (team `rattsnest.cloudflareaccess.com`, Google login, policy = one email). Access handles login/sessions; unauthenticated requests get redirected to Google before reaching the Worker.
- The Worker **also** verifies Access's JWT on every `/api/admin/*` request (`worker/access.ts`: signature against the team's certs, `aud`/`iss`/`exp`, and `email === ADMIN_EMAIL`), failing closed — don't remove this on the assumption Access is always in front. `ACCESS_TEAM_DOMAIN`/`ACCESS_AUD` are plain `vars` in `wrangler.jsonc`; `ADMIN_EMAIL` is a Worker secret (`wrangler secret put ADMIN_EMAIL` in prod, gitignored `.dev.vars` locally) so the address stays out of this public repo — if it's unset, every admin request 401s.
- Routes: `/api/admin/me` (admin check), `/api/admin/status` (`meta:admin`), both `Cache-Control: no-store`; `/logout` redirects to Access's `/cdn-cgi/access/logout`.
- The Admin tab's visibility (`GetIsAdmin` in `data/GetAdminStatus.ts`, `redirect: "manual"` so Access's login redirect reads as "not admin") is UX only — the Worker is the actual lock. `meta:admin` can contain raw exception text (possibly URLs with API keys), so never expose it through a public route.
- No auth bypass for local dev: `wrangler dev` has no Access in front, so admin routes 401 locally. Mock `/api/admin/*` in the browser instead.

### Deployment

- Hosting is Cloudflare Workers + Static Assets, live at <https://morlocked.rattsnest.com/>. Pushing to `main` deploys automatically; `npm run build && npm run deploy` still works for a manual deploy. The previous IONOS Deploy Now GitHub Actions workflow has been removed along with IONOS hosting.

## Migration history

This app was migrated off Firebase Realtime Database + IONOS hosting onto the Cloudflare Worker/KV architecture described above. The migration is complete as of 2026-09-21 (`v2` merged into `main`, IONOS workflow removed, DNS live on Cloudflare). `CLAUDE.local.md` (gitignored, not committed) has the full decision history from the migration and tracks current post-cutover (phase-2) work — check it before assuming a feature is or isn't built yet.
